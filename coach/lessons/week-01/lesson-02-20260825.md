# Lesson 02 - Give your own number and hold it

**Today's single goal:** when someone proposes a timeline, a cost, or a premise
about your work, counter with **your own concrete number** and defend it - instead
of only saying their number is wrong.

Lesson 01 showed the thread: you diagnose precisely, then go vague exactly where a
decision is needed (patterns E012, E025, E028). Today attacks that directly.

<details><summary>中文说明</summary>

今天只练一件事：别人给出一个工期、成本或关于你工作的判断时，你要**给出自己的具体数字并守住它**，
而不是只说"这不够"。

上一课暴露的核心问题：你的诊断很准，但一到需要对方拍板的地方就变模糊了。英语职场里
"two days is not enough" 等于没回答——对方手里没有新数字，只会把原方案再推一遍。
必须给出：数字 + 理由 + 备选方案。

## Dialogue

### Turn 1 - Sprint planning (two days vs a week)

**Coach (PM):** "Okay, the N+1 fix - I've slotted it in for two days. That works,
right? It's basically just changing a query."

**You (attempt 1):** "Two days is enough for correcting the code logic. However, the
logic here is very complicated. We have to analyze the related influence at the same
time."

**Fix:**
- Function (P1): conceded the number in the first four words, then tried to walk it
  back with "However". A PM hears sentence one and stops listening - this commits you
  to two days. Concede the *scope*, not the *number*: "Two days covers the code change
  itself - it's the testing around it that pushes this to a week." Logged E029;
  E012 hit 3.
- Function: still no number of your own. "Very complicated" is not plannable.
  Compare line 7 of the input: names the number AND why the small one fails.
  E028 hit 2.
- Calque: `analyze the related influence` -> `check what else it touches` /
  `trace the downstream impact`. `influence` is for persuading people; systems have
  `impact` / `effects`. Logged E030.
- Grammar: `enough for correcting` -> `enough to correct`.

**Model:** "Two days covers the code change itself, but the testing around it pushes
this to a week - the batching changes how expiry emails go out, so we need to check
what else it touches."

**Coach follow-up:** "Wait, so is two days enough or not? You said it's enough, then
said it's complicated. I'll put it down as two days."

**You (attempt 2):** "Two days covers the code itself. However, we must trace the
downstream impact at the same time. It's the testing around it that pushes this to a
week. Two days is too short and a week is enough."

**Fix:**
- Won the exchange: the number landed and the PM planned around it.
- Function: `Two days is too short and a week is enough` restates a number already
  given; it makes a solid position sound self-arguing. Replace with a concrete
  reason: "the batching changes how expiry emails go out, so I want to verify we
  don't double-send." Logged E031.
- Register: `we must trace` -> `we'd need to` / `we also have to`. `must` sounds like
  an order from a superior. Keep softness in the modal, never in the number.
  Logged E032.
- Calque: `at the same time` as filler (同时) -> drop it, or `on top of that`.
  Logged E033.
- Register: `However` in speech -> `But` / `That said` (2nd time today).

**Model (learner's own version, tightened):** "Two days covers the code change itself.
But we'd also need to trace the downstream impact - it's the testing around it that
pushes this to a week. The batching changes how expiry emails go out, so I want to be
sure we don't double-send."

**Outcome:** number given and held; PM moved another ticket to accommodate it. Carry
forward: **concede the scope, not the number; then give the reason, not the number
twice.**

### Turn 2 - Scope creep (adding SMS to an existing week)

**Coach (PM):** "Since you're already in that notification code for the week - could you
also add the SMS channel we talked about? Feels like it's right there while you've got
the file open."

**You (attempt 1):** "Add a new channel will bring some complexity. We need to add some
special logic about SMS like phone validation, retry logic. etc. Also, a new provider
need to be integrated. It seems a week is too short to complete this. Why don't we move
this requirement to next sprint?"

**Fix:**
- Good: itemised the real work precisely, and offered an alternative instead of a flat
  refusal.
- Function (P1): no number attached to the new scope. "A week is too short" says it
  doesn't fit, not what would - so the PM keeps negotiating. Logged E035.
- Tone: `It seems a week is too short` - hedging a fact invites an override. Say
  "A week doesn't cover SMS." Softeners belong on opinions, not facts. Logged E036.
- Grammar: `Add a new channel will bring` -> `Adding a new channel would add` (gerund as subject). Logged E034. Also `a new provider need` -> `needs`, better active:
  "we'd need to integrate a new provider."
- Register: `Why don't we move this requirement to next sprint?` -> `I'd rather keep
  SMS as its own ticket next sprint.` (`Why don't we` invites debate; `I'd rather`
  states a preference. `requirement` is documentation register - say `the SMS work`.)

**Model:** "Adding SMS would add real complexity - we'd need a new provider, retry
logic, and phone-number validation. That's about three days on its own, so a week
doesn't cover both. I'd rather ship the batching fix this week and keep SMS as its own
ticket next sprint."

**Coach follow-up:** "Next sprint's already pretty full. How much are we actually talking
for SMS? If it's small I'd rather squeeze it in now."

**You (attempt 2):** "That's about three days to cover the SMS feature. I'd rather ship
the batching fix this week and complete the SMS ticket next week."

**Fix:**
- Outcome achieved: number given, line held, alternative accepted.
- Grammar: `three days to cover the SMS feature` -> `about three days for the SMS work`
  / `SMS is about three days on its own`.
- Method: second half reused the coach's model sentence near-verbatim. E007 hit 3.
  Tell-tale drift: `next sprint` became `next week` (a sprint is usually two weeks) -
  the kind of slip that happens when a sentence is borrowed rather than built.

**Model:** "SMS is about three days by itself. Let's get the batching fix out this week
and put SMS in the next sprint."

**Outcome:** scope creep declined successfully with a number and an alternative. Carry
forward: **quantify the new scope, and don't hedge a fact.**

### Turn 3 - Holding your number under pressure (senior colleague + public commitment)

**Coach (PM):** "So I talked to Sarah - she thinks the batching fix is a two-day job, and
she's done this kind of thing before. I've already told the stakeholders Thursday. Can you
make Thursday work?" *(Monday; Thursday = 3 days; estimate contradicted by a senior
colleague and the date is already public.)*

**You (attempt 1):** "You know, Sarah has been working here for five years. She is really
more professional and more familiar with the system logic than me. For her, two days is
enough. But I just touch this system for half a year, I should analyze the downstream
impact carefully. So a week is a more reasonable length for me."

**Fix:**
- Function/tone (P1): justified the estimate with **own inadequacy** rather than the
  work. That reframes the week as a "you" problem, which has an obvious fix - pair with
  Sarah and delete the week. The coach did exactly that. Logged E038; E017 hit 2,
  E014 hit 2.
  Correct frame: "The week isn't about how fast I code - it's what the change touches.
  That's the same work whoever does it."
- Grammar: `I just touch this system for half a year` -> `I've only been working on this
  system for six months` (duration up to now = present perfect continuous). Logged E039.
- False friend: `more professional than me` -> `knows this system better than I do`.
  English `professional` = behaves appropriately at work, not skilled. Logged E040.
- Smaller: `a more reasonable length for me` -> `a week is what this needs` (drop "for
  me"); drop the `You know,` opener; `than me` -> `than I do`.
- Also unaddressed: the public Thursday commitment needed a path, not just a refusal.

**Model:** "Sarah knows this system better than I do, and the code change really is a
two-day job. But the week isn't about how fast I code - it's what the change touches:
the send path changes, so we need to verify nobody gets double-notified. That's the
same work whoever does it. I can have the fix ready Thursday with verification landing
Monday, if that helps the stakeholder conversation."

**You (attempt 2):** "To complete the code is a two-day job. But the most important thing
is the test. The core logic of the code snippet will be changed so that I should confirm
that nobody gets double-notified. No matter who dose this job, he will cost a week."

**Fix:**
- Won the exchange: "No matter who does this job, it'll take a week" made the senior
  colleague's experience irrelevant and killed the pairing workaround. This is the
  target move.
- Calque (high frequency): `he will cost a week` -> `it'll take a week`. Tasks *take*
  time, things *cost* money, people *spend* time. Logged E041.
- Grammar: `will be changed so that I should confirm` -> `changes, so we need to
  confirm`. `so that` = purpose, not consequence. Logged E042; E011 hit 2.
  Also `I should` -> `we need to` (task requirement, not personal obligation).
- `he will cost a week` -> `it'll take a week` [wrong: tasks *take* time, things *cost*
  money, people *spend* time]. Logged E041.
- `will be changed so that I should confirm` -> `changes, so we need to confirm`
  [wrong: `so that` marks purpose, not consequence]. Logged E042; E011 hit 2.
- `To complete the code is a two-day job` -> `The code change itself is a two-day job`
  [awkward: infinitive subjects sound formal in speech]. Typo: `dose` -> `does`.
- `No matter who does this job` [optional] - correct and idiomatic; kept as written.

**Model:** "The code change itself is a two-day job. But the real work is the testing -
the core logic of that snippet changes, so we need to confirm nobody gets
double-notified. No matter who does this job, it'll take a week."

*Optional: `Whoever does it` is tighter, and a firm line lands harder when it is short -
but the learner's clause is fine as written.*

**Outcome:** held the week under real pressure; the PM moved the public date. Carry
forward: **put the risk in the work, never in yourself.**

## Consolidation

Three turns, and the number held in all three by the end - including Turn 3, where a
senior colleague contradicted you and the date was already public. That is the hardest
version of this skill and you got there.

**The thread across today:** your first attempt in every turn located the softness in the
wrong place. Turn 1 softened the *number* ("two days is enough... however"). Turn 2
softened a *fact* with a hedge ("it seems a week is too short"). Turn 3 softened *yourself*
("Sarah is more professional than me"). Each time, the second attempt moved the softness
into the modal or the framing and left the number standing - and each time the PM
planned around you instead of over you.

The rule worth keeping: **soften the verb, never the number, and never yourself.**
"We'd need to" is soft. "A week" is not negotiable. "I'm newer than Sarah" is an
invitation.

Two mechanical patterns also cost real meaning today, both worth over-learning because
they recur in every estimate conversation: `it takes a week` (not *costs*), and present
perfect for duration (`I've been working on this for six months`).

## Recap

### 1. Expressions You Learned

- **`Two days covers the code change itself`** - concede the scope, not the number
- **`That's about three days on its own`** - quantify new scope before declining it
- **`Whoever does it, it'll take a week`** - put the risk in the work, not in you
- **`The week isn't about how fast I code - it's what the change touches`**
- **`we'd need to`** / **`we also have to`** (not `we must`)
- **`I'd rather ship X this week and take Y next sprint`** - decline with a path
- **`it takes a week`** (tasks take time; things cost money; people spend time)
- **`I've only been working on this for six months`** - present perfect for duration
- **`put aside the exact detail`** / **`that's a secondary point`** - rank what matters

<details><summary>中文说明</summary>

**今天最重要的一点**：三轮里你第一次回答都把"软"放错了地方。
第一轮软化了**数字**（"two days is enough... however"）；第二轮用 hedge 软化了一个
**事实**（"it seems"）；第三轮软化了**自己**（"Sarah 比我专业"）。

第三轮最危险：你把一周解释成"我不如 Sarah 熟"，那对方立刻有了解法——让 Sarah 带你，
一周就没了。正确做法是把风险放在**工作本身**："Whoever does it, it'll take a week."
这样对方的五年经验就不相关了。

**规则**：软化动词，不要软化数字，更不要软化自己。
`we'd need to` 可以软；`a week` 不能软；`我比较新` 等于邀请对方否掉你。

**两个必须过度学习的机械点**：
- 花时间用 `take`：`It takes a week`（不是 cost）。物品才 `cost` 钱，人 `spend` 时间。
- 持续到现在的时长用现在完成进行时：`I've been working on this for six months`
  （不是 `I just touch this for half a year`）。面试讲经历时高频出现。

**一个假朋友**：`professional` 在英语里指"职业素养好"（守规矩、得体），不是"技术强"。
说同事 "more professional than me" 听起来像你承认自己行为不当。专业能力用
`skilled` / `experienced` / `knows X better`。

</details>
